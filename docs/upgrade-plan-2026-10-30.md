# Monitors Focus 项目全面审查与升级规划

审查日期：2026 年 10 月 30 日。代码基线：`28c9c38`，当前应用版本 `1.0.0`。本文面向项目所有者与后续开发者，作为重做的范围、技术决策和验收依据。

建议将项目升级为个人使用优先、兼顾开源分享的 Windows 显示器控制中心：保留鼠标跟随的自动专注功能，增加双屏手动亮度、按比例绑定、时间计划与渐变、场景快速切换，并重做 UI 和交互。先修复硬件控制底座，再迁移界面与增加策略，分阶段替换现有实现。

审查时基线规模为 18 个 C# 文件、约 2,037 行源码、一个应用项目；当前已开始迁移，最新结构见开发说明。大幅重做具备可控性；主要成本来自显示器兼容性、亮度策略冲突和真实使用体验，而非文件数量。

首版建议聚焦 Windows 11 x64 和用户实际双屏环境。Windows 10、ARM64、环境光感应、应用触发、HDR 专项适配作为后续兼容或功能扩展，是否支持以实测为准。保留第三块屏幕的模型扩展能力，但不为此引入插件系统。

## 当前项目的整体判断

目前是一个 Windows 桌面应用，没有独立 Web 前端、服务器后端、数据库或云服务。“前端”对应设置窗口、托盘和遮罩；“后端”对应本地控制策略、显示器枚举、DDC/CI、WMI、热键及配置持久化。升级应围绕这些真实边界进行。

现有按功能分目录的基础是合理的，依赖很少，遮罩、热键、监测已有初步分工。问题集中于：策略状态依赖 UI 对象，硬件会话生命周期不安全，身份与能力模型过于简单，设置窗口承载过多任务，工程资料与实际代码不同步。

优先级定义：P0 为发布前必须处理的原生安全与恢复问题；P1 为核心正确性和新产品的前置能力；P2 为体验、维护和工程流程；P3 为使用需求尚不足以支持的扩展。

## 新版本功能规格建议

### 手动亮度与比例绑定

两屏都有独立名称、亮度滑条和数值输入。数值指设备控制百分比，不能承诺不同屏幕相同百分比具有相同物理亮度。支持用户别名和短暂编号识别；检测不到硬件能力时，明确显示“硬件亮度不可用”，软件遮罩作为独立选择。

启用绑定时保存非零比例权重和一个共同强度。例如权重 40:60，以 50% 共同强度得到 20:30。以一个共同系数同时计算各屏值，整体限制系数，使任何屏不超过其允许上限；不要逐屏截断后悄悄破坏比例。若第二屏达到 100%，第一屏最高约为 66.7%，UI 应解释为何无法继续拉高。

全组降至 0% 时保留之前的非零权重，重新拉高后恢复比例。首次绑定时若某屏为 0%，提示先设置非零基准或将该屏排除，避免除零和永久零值。设备档位和整数舍入可能造成少量偏差，验收按最近合法档位计算。绑定状态下任一成员调节都改变共同系数；需要改变比例时先解绑再调整后重绑。

高频拖动只更新最新目标，控制器合并写入；界面区分目标值、正在应用与失败状态。一个设备失败时保留其他设备成功结果，显示“部分应用”，提供重试，避免为了表面一致反复调节成功设备。

### 时间计划与渐变

每个时间节点保存本地时间、目标场景或逐屏亮度与色温目标，以及过渡时长。两种目标共用时间轴，但各自按能力和变化精度更新；支持单独关闭其中一种。第一版使用固定时间；白天、傍晚、夜间是可编辑示例，不依赖定位或传感器。

建议采用“到达节点后，从当前有效目标向新目标渐变”的清晰语义。过渡时长为 0 即刻切换；下一节点到达时接管目标，停止旧过渡。系统启动和休眠恢复时直接计算此刻应处的位置，不补执行所有错过的节点。跨午夜、重复时间点、系统时钟回拨与跳时应有确定结果；重复节点在编辑时阻止保存。

手动调整或手动切场景立即停止当前渐变，并保持到下一个计划节点；同时提供“恢复计划”。这是推荐默认规则，需在交互原型时确认。用户始终能看到当前亮度来自手动、场景还是时间计划，及下一次计划变更时间。

### 场景快速切换

场景包含名字、逐屏基准亮度和色温目标、绑定组及权重、专注是否启用和受控屏规则。亮度比例绑定仅作用于亮度；色温不按亮度比例缩放，可由同一场景分别指定。时间计划引用场景，复用同一执行路径。托盘面板展示常用场景，快捷键可直接切换；配置编辑在完整窗口中完成。

### 色温渐变的技术验证

目标体验是在同一时间段内缓慢变暗、变暖，例如从日间状态过渡到夜间状态。色温显示为 K 与冷暖预览，但实际白点受显示器影响，未经校准不承诺数值对应精确测量值。专注调暗默认不额外改变色温，避免鼠标跨屏导致颜色来回跳变。

优先探测设备支持的色温控制。Windows 的 SetMonitorColorTemperature 只能设置设备支持的枚举档位，不能据此承诺连续平滑渐变。设备若提供可用的 RGB 增益等细粒度能力，可以在实际双屏上评估平滑性、原色恢复和写入成本；只有硬件档位时，必须明确为分档切换，不能把它当作已满足缓慢平滑变化。[Microsoft 色温接口说明](https://learn.microsoft.com/en-us/windows/win32/api/highlevelmonitorconfigurationapi/nf-highlevelmonitorconfigurationapi-setmonitorcolortemperature)

软件 Gamma 变换仅作为兼容性实验候选，不作为默认稳定方案。微软明确不推荐 SetDeviceGammaRamp，指出其他程序和显示变化可能覆盖结果，HDR 与色彩校准交互未定义，返回成功也不一定实际应用。首版验证实际 SDR 环境、夜间模式、现有 ICC 配置、显卡驱动、全屏和插拔；HDR 平滑调色不纳入首版承诺，检测到 HDR 时停用未经验证的色温路径并提示用户；不将反复抢写 Gamma 当作可靠恢复，也不以未公开的夜间模式注册表修改作为主路线。[Microsoft Gamma 接口限制](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-setdevicegammaramp)

M1 增加色温可行性关卡：在用户真实两屏验证一条可恢复、长期低占用的色温路径。若仅有不稳定或分档控制，保留亮度功能并明确色温尚未达标，回到用户讨论兼容范围或过渡要求，不能宣称完整目标交付。暖色透明遮罩不能作为等价的色温控制悄悄替代。

色温适配器单独报告能力、当前控制方式和失败；亮度成功、色温失败时显示部分应用。保存原始颜色状态与会话归属，提供“一键恢复原色并暂停色温”；退出时恢复本应用临时颜色变换，避免覆盖外部程序后续调整。设备恢复和崩溃重启的处理需单独验收。是否将硬件色温场景永久保留，在实机原型时确认。

渐变只存少量端点参数和当前目标，后台按可见精度限频更新，不持续生成动画帧或逐帧分配颜色表。界面关闭后亮度和色温计划仍运行。色温能力试验与恢复验证列为工程前置工作，而非最终发布前补测。

首版可提供“日常”“夜间”“专注”三个可编辑起点，具体百分比由用户实际屏幕试调后保存。保存当前状态时默认保存基准亮度，不把临时专注调暗后的亮度误存为常用场景。场景引用离线屏幕时保留配置，标示未应用对象，不把目标错配给其他屏幕。

### 与自动专注共存

必须将“正常应有多亮”和“暂时为了专注而调暗”分成两层。手动、场景和时间计划产生基准亮度；专注层只对其叠加临时限制。鼠标返回时恢复最新基准，不能恢复启动时亮度。

例：副屏基准为 60%，专注临时降至 10%；夜间计划把基准改为 30%。鼠标返回副屏，应恢复 30%。这条规则同时解决现有恢复旧亮度问题和新计划功能的冲突。

| 行为 | 建议结果 |
| --- | --- |
| 手动调节正在专注调暗的屏幕 | 立即临时唤醒，修改基准，重新开始专注倒计时 |
| 手动切场景 | 应用场景基准和专注规则，保持至下一计划节点或主动恢复计划 |
| 暂停专注 | 清除临时遮罩与调暗，保留基准亮度和时间计划 |
| 暂停全部自动化 | 保留当前正常基准，不再执行计划或专注，手动控制仍有效 |
| 退出应用 | 移除遮罩、恢复临时专注改动；保留用户手动/场景设定的正常亮度 |
| 紧急恢复可见 | 优先移除遮罩并请求恢复正常基准；可从托盘及独立热键操作 |
| 检测到外部亮度变化 | 按可验证读回更新基准或提示冲突；不在后台持续抢写 |

建议在新控制器启用写入后关闭 Twinkle Tray 对相同显示器的自动调节，避免两个程序同时控制。首版不自动结束其他软件，也不承诺能可靠识别所有外部控制者。

## UI 与交互重做方案

### 页面分工与日常路径

界面围绕“调亮度、切场景、管理自动化”组织。托盘点击应打开快捷面板，不再直接打开大设置表单。

| 界面 | 内容与优先级 | 关键交互 |
| --- | --- | --- |
| 托盘快捷面板 | 双屏名称与滑条最突出；绑定控制紧邻滑条；常用场景其次；当前自动化来源及暂停入口 | 一次点击打开即可调节；一键绑定、切场景；键盘直接操作滑条；点击外部关闭 |

| 时间计划 | 同一时间轴上的亮度与色温目标、渐变时长 | 添加/编辑节点，展示下一次执行；两条目标曲线可分别开关，提示设备实际支持方式 |

正常使用路径：点击托盘 → 拖动任一屏滑条或选场景 → 硬件异步应用 → 用户继续工作。初次设置路径：识别两屏 → 确认各屏控制能力 → 调整合适基准 → 绑定或保存场景 → 配置时间计划 → 选择是否启用专注。

首次检测失败不能让整个产品不可用。仍可访问设置、使用可用屏幕和纯遮罩专注；无法写入的屏幕禁用对应操作，并保留清楚的重试入口。

### 视觉与可访问性

建议采用克制的 Windows 原生桌面风格：清晰字体、充足但紧凑的间距、直接滑条、少量状态文字。显示器行不套多层卡片；不把日志、DDC/CI、WMI 术语放进主要操作区。状态不能仅靠颜色表达。

## 技术路线与架构建议

### 桌面技术选择

用户已确认采用 **React + TypeScript + Tailwind CSS + shadcn/ui + Motion + Lucide**，由 **C# WebView2** 承载。WinUI 3验证阶段已结束，不继续维护两套界面；本轮不引入Tauri或Rust。界面沿用已选A方案，以实际截图、三档无衬线字号、统一参数和连续曲线验收。

这一调整优先满足精确还原和快速调试：CSS变量与Tailwind统一参数，shadcn组件在项目内维护，浏览器工具支持样式检查。代价是面板打开时的WebView2进程开销、冷启动和通信层；关闭后释放界面进程，核心继续低频调度，性能以实测为准。

系统接口稳定性由设备识别、原生封送、串行命令和生命周期决定。系统控制保留C#/.NET、Win32/WMI，前端只发明确命令，不接触设备句柄。生产界面加载本地静态资源，不运行Node或HTTP服务器。

当前实现与运行入口见[开发与构建](development.md)。以下资源与硬件验收要求继续有效。
### 持续低占用与自动启动

优先验证“轻量常驻核心 + 按需启动的 UI 进程”：常驻核心负责托盘、热键、调度、设备会话与遮罩；WebView2 界面打开时连接核心，关闭后退出 UI 进程。这样可以释放整个界面运行时的进程资源，而不是仅隐藏窗口。代价是 IPC、UI 冷启动和两个进程同时运行时的内存峰值，需在 M1 样例阶段测量。若单进程方案已满足长期占用预算且体验明显更好，可选择单进程，不为了形式坚持拆进程。

跨进程只传命令与状态快照，设备句柄仅由常驻核心拥有。采用限制到当前用户的本地命名管道，定义协议版本与断线重连，不监听网络端口。关闭或重启 UI 不影响计划运行；核心退出时 UI 必须显示离线，不能假装控制成功。此处的 UI 进程分离用于释放界面资源，与后文可选的硬件工作进程故障隔离是两种不同目的，不默认形成三个常驻进程。

常驻核心运行在当前登录用户的桌面会话中，使用用户级自启。通常所说“开机自启”在本产品中指登录后启动；在登录前控制登录界面的屏幕属于额外需求。首版不安装 LocalSystem Windows 服务：Windows 服务与交互桌面具有会话隔离，托盘、鼠标和遮罩需要用户会话。[Microsoft 交互服务说明](https://learn.microsoft.com/en-us/windows/desktop/Services/interactive-services)

自动启动优先保证托盘可用，硬件探测异步进行，设备暂未就绪时使用有界退避；不启动完整设置窗口、不申请管理员权限、不启动重复实例。关闭自启应能读回实际状态，升级移动安装位置后应同步自启入口。登录后按当前时间计算计划目标，不重放关机期间的渐变步骤。

长时间亮度渐变由核心按时间公式计算，不依赖 UI 动画或每帧刷新。只保存起点、终点、开始时间和时长，按设备可表达的下一档亮度安排更新；最终目标不变时不重复写入。手动调节优先接管，休眠期间无需持续计时，恢复后重算当前值。专注鼠标监测与渐变调度分开；专注暂停时停止不必要的鼠标轮询。

日志、设备读回和状态推送均限频、有界，关闭界面时不产生界面刷新。长期性能同时测私有内存、工作集、CPU、唤醒次数和硬件写入次数，避免只让任务管理器瞬时数字好看。微软也建议减少后台工作并释放后台图形资源；这支持设计方向，但不能代替本项目的测量结果。[Microsoft 内存与后台资源建议](https://learn.microsoft.com/en-us/windows/apps/develop/performance/disk-memory)

### 模块边界

当前工程采用以下结构，不预建空项目：

```text
src/
  MonitorsFocus/          # 当前常驻核心、Windows适配、兼容旧版入口
  MonitorsFocus.Core/     # 协议、比例与每日计划纯计算
  MonitorsFocus.Web/      # React/TypeScript界面和设计参数
  MonitorsFocus.WebHost/  # WebView2窗口、本地资源和命名管道桥
scripts/build.ps1         # Web优先构建与打包
tests/MonitorsFocus.Tests/ # 假设备生命周期检查
```

后续仅在职责复杂度确实需要时，从现有核心拆Windows适配模块。Core不引用UI、注册表或WMI；WebHost不实现亮度策略。生产包同时包含desktop和core两个目录，前者按需运行，后者持有设备句柄。审查基线与原有缺陷列表保留作为迁移验收依据，不把其状态误当成当前已修复结论。
核心数据包括 DisplayIdentity、Capabilities、BaseBrightness、FocusOverride、LinkGroup、Scene、Schedule、OperationResult。UI 展示状态快照，不直接操作可变会话字典。

### 命令仲裁与故障恢复

所有手动、计划、场景和专注动作通过一个控制器计算最终目标。每台物理设备只有一个执行队列，写入合并为最新目标；硬件调用不占 UI 线程，不因拖动滑条创建无限任务。

设备会话带代次；拔插或重新枚举后，旧代次结果不得修改新会话状态。取消等待不代表取消 DDC 原生调用，禁止在在途调用使用句柄时释放。有限超时负责让 UI 可继续工作，不伪装成设备已经恢复。

第一阶段用有界队列和正确生命周期；若真实驱动持续挂住，影响退出或资源回收，再引入独立硬件工作进程隔离。进程隔离有 IPC、重启和部署成本，应由硬件实测触发，而不是默认建立服务体系。

崩溃恢复只保存最小临时调暗记录与设备身份。下次启动发现未恢复记录时，重新读取当前状态并核对，不能盲目向新接入屏写旧亮度。对驱动永久无响应不承诺软件能强制恢复，保留用户可理解的设备失败提示。

## 配置迁移与发布管理

旧配置位于 `%AppData%\Monitors-Focus\settings.json`。新模型增加 schemaVersion，先备份旧文件再迁移；保留延迟、遮罩、语言和热键，新增场景/绑定/计划使用明确默认值。旧 DeviceName 的映射不可靠时引导用户确认屏幕，而非静默绑定。

采用独立的新格式文件名，避免旧版本误写新数据。迁移幂等，重复启动不重复覆盖用户修改；未知字段尽量保留，未知未来版本阻止破坏性降级。回滚需同时准备旧可执行文件和对应旧配置备份。迁移期间两个版本不能同时控制同一硬件。

版本号以项目构建配置为唯一来源，Release 说明从实际变更生成。保留便携包作为个人使用首选；需要安装时再提供用户级安装和卸载，清理自启项。首版可手动下载更新，不为个人使用引入自动更新后台服务。公开分发前再决定签名与安装器投入，并公布校验和。

CI 的最小范围是 Windows 上还原、构建、核心测试和打包检查；硬件矩阵由本机验收记录补充。构建成功不自动发布，发版必须满足阶段验收并经过明确发布动作。

项目管理使用按用户结果拆分的工作项，例如“绑定后保持比例”“夜间计划不覆盖刚刚手调”，每项附验收条件和所属阶段。维护一个简短决策记录与当前文档索引，替代历史模板要求的逐微步骤日志和无止境重复审查。历史日志保留其时间背景，不改写成当前状态。

| M2 手动亮度控制 | 稳定身份、异步探测、逐屏滑条、按比例绑定、快面板、单实例 | 两屏正确控制；40/60→20/30；零值恢复与触顶规则通过；失败可见 | 5–8 天 |
| M3 场景与时间计划 | 场景保存/切换、快捷键、亮度与色温计划、渐变、手动覆盖、休眠恢复重算 | 共用时间轴；分别报告能力；跨午夜与睡眠后正确；手动操作不被旧渐变覆盖 | 原亮度范围 5–8 天；色温部分在 M1 后估算 |
| M4 专注整合与迁移 | 临时专注层、最新基准恢复、模式语义、旧配置迁移、完整界面与本地化 | 专注期间计划更新后正确恢复；保留原有鼠标唤醒；旧配置可回滚 | 4–6 天 |
| M5 实机验收与开源交付 | 硬件矩阵、可访问性、长期运行、便携包、README/截图/发布说明 | 用户双屏日常流程通过；无阻断问题；发布包可追溯、可回滚 | 3–5 天 |

原亮度与界面范围约 24–39 个有效工作日，另预留约 20% 硬件与体验调整缓冲。新增已确认的色温需求后，该区间不再代表完整项目总工期：M1 先增加约 2–4 天色温可行性验证预算，验证实现路径后补估 M3/M5；若无可靠路径，先确认取舍，不给虚假的完整交付日期。若采用 UI 分进程，也按协议与部署实测重估 M2。个人可用里程碑为 M2；全部已确认功能的交付出口仍为 M5。

依赖顺序为 M0 → M2 → M3 → M4 → M5；M1 的设计工作可在 M0 后段推进，但最终界面扩展要等待代表性路径确认。运行时支持窗口很近，若完整重做跨过 11 月 10 日，应先形成修复版底座，避免继续分发旧运行时。

## 验收矩阵与性能预算

不追求覆盖率数字。自动测试集中在容易产生严重回归的纯计算、仲裁和硬件生命周期；UI 以代表性操作与截图验收，真实设备只测软件无法模拟的行为。

| 领域 | 必测案例 | 通过标准 |
| --- | --- | --- |
| 原生布局 | x64 PHYSICAL_MONITOR 大小与字段偏移 | 与原生定义一致 |
| 会话时序 | 慢调暗、快速恢复、刷新、退出、旧任务晚完成 | 不使用已释放句柄；最终最新目标获胜；旧代次不污染新状态 |
| 设备隔离 | 两屏中一屏失效、WMI 无法映射、拔插重编号 | 不误调另一屏；失败不会阻塞其他屏和 UI |
| 比例绑定 | 40/60→20/30、触顶、全零后恢复、离散档位 | 权重保存，整体限幅，误差不超最近合法档位 |
| 时间计划 | 跨午夜、启动、休眠恢复、跳时、渐变中拖动 | 计算当前目标；旧过渡停止；手动保持规则一致 |
| 色温 | 实际双屏 SDR 长时间渐变、原色恢复、夜间模式/现有 ICC 冲突、休眠与显示变化，以及开启 HDR 后停用未验证路径 | 达到约定的平滑度；失败可见；不破坏原有颜色状态；不支持路径明确停用 |
| 专注恢复 | 60% 基准→临时10%→计划30%→鼠标返回 | 恢复30%，遮罩即时消失 |
| 配置 | 旧格式、半写文件、保存失败、重复迁移、回滚 | 旧文件可恢复；失败可见；不覆盖用户有效设置 |
| UI | 中英文、缩放、键盘、离线、检测中、部分应用失败 | 关键操作可达、状态准确、无文本截断和业务值丢失 |
| 系统集成 | 单实例、热键冲突、带空格安装路径、自启、Explorer 重启 | 可从托盘/快捷键恢复操作；自启状态与实际一致 |
| 实机体验 | 用户两屏、不同刷新率与布局、拖拽跨屏、锁屏/睡眠、24小时运行 | 不重排窗口；可唤醒；无持续资源增长或控制抢写 |

首版建议性能预算：快捷面板交互反馈 P95 小于 100ms，遮罩移除 P95 小于 100ms；硬件亮度完成时间单独按设备记录，不与遮罩速度混为一谈。托盘可用冷启动目标不超过 2 秒，设置窗口暖启动不超过 500ms。空闲 CPU 平均目标不超过单机总 CPU 的 0.5%，至少记录 5 分钟测量窗口。

持续低占用作为选型门槛：测“登录后仅托盘”“UI 打开”“UI 关闭后”“两小时缓慢渐变”“24 小时运行”五种状态。明确私有内存与工作集口径，多进程按合计统计；记录 UI 关闭后的回落情况和完整冷启动成本。以样例测量提出具体内存上限，确认后才扩展全部页面，不沿用未经核验的 20MB/30MB 宣传。不得通过反复强制 GC 或裁剪工作集伪造低占用；重点观察私有内存、句柄、任务队列是否持续增长。

## 后续决策与开工入口

已确认亮度与色温共同按时间渐变、仅 Windows、持续低占用与用户级自启要求；以下细节在 M0/M1 内解决：实际显示器型号及连接方式、SDR 色温适配和恢复路径、手动保持规则、场景默认内容、WebView2按需宿主与资源释放表现、Windows 版本范围与视觉方向。

建议第一批工作项按顺序创建：原生结构修复 → 硬件队列与恢复 → WMI 身份匹配 → .NET 10 与最小测试 → 双屏控制原型。第一份界面交付应为“快捷面板 + 时间计划 + 场景编辑 + 错误状态”的成套效果图，确认后实现可运行主路径。

本轮没有执行功能重写、框架迁移、硬件操作或发布。报告中的目标结构、功能规则建议及工作量用于后续实施决策；已确认需求与仍需原型确认的规则已分别标明。
